# Research: how competing apps handle expense entry and splitting

Checked: 2026-10-16 (UTC). Features and pricing change often, so re-check them before you commit. Entries marked **UNVERIFIED** could not be confirmed from a primary source. Primary sources here are each vendor's help center, official site, official feedback forum (staff replies only), API docs, App Store / Google Play listing text, and, for Spliit, its source code. Store-listing **reviews** and **user comments** on vendor forums are not vendor claims. They are labelled "(user signal)". "(source)" marks claims read from the Spliit repository at commit `5dac411` (2026-10-13), [github.com/spliit-app/spliit](https://github.com/spliit-app/spliit).

## 1. Our format (baseline)

Read from this repo so the comparison uses what the code actually does, not what we intend it to do.

- Creating an expense takes a name and a total. Currency defaults to the trip currency, and the payer defaults to the current member (`client/Trip.tsx` `createExpense`). The create call inserts **no participants** (`server/index.ts` `POST /api/trips/:token/expenses`). The user then lands on the expense page with the whole total unassigned.
- Participants are ticked one at a time under "Who's in". Each tick is a separate request (`PUT /api/expenses/:id/participants`). A ticked participant starts with `share_minor = NULL`.
- Effective share = typed amount + an equal portion of each item they share (`effectiveShares`). Unassigned = total − sum of effective shares (`expensePayload`). Over-assignment is allowed and shown as "over by X" (`client/Expense.tsx`).
- Helpers: "Split unassigned equally" (`equal_rest`) gives the rest only to participants whose typed share is still `NULL`. "Spread unassigned proportionally" adds the rest in proportion to current effective shares.
- Balances count only non-null effective shares. Unassigned money is owed to nobody (`balancesForTrip`). The settlement view is pairwise net, with no debt simplification (`balancesForTrip`, "net pairwise").
- FX: the rate is locked when the expense is created, and locked again only if the currency changes (GLOSSARY "Locked Rate"; `lockRate`). The source is Open Exchange Rates, refreshed on a loop, with Frankfurter as fallback (`server/fx.ts`). There is no UI to override the rate manually (`client/Expense.tsx` shows the rate read-only).
- Anyone in the trip can edit any expense. Only the "last edited by" name and time are stored (`edited`, `last_edited_by`). There is no per-change history.
- There is one payer per expense (`payer_member_id`).

Common case, "I paid X, split equally among everyone": type name → type total → Create → tick each of N members → "Split unassigned equally". That is about **N + 4 actions across two screens** (counted from the code above, not measured on a device).

## 2. Per-app findings

### 2.1 Splitwise

1. **Split modes:** Equally (default), exact amounts, percentage, shares, adjustment ("the rest of the expense will be split equally among everyone else"), reimbursement (web only), and itemized. [KB: ways to split](https://kb.splitwise.com/balances-and-expenses/what-are-different-ways-i-can-split-an-expense). Multiple payers are supported: "Add multiple payers on a single expense" [App Store](https://apps.apple.com/us/app/splitwise/id458023433). On the web, choose "2+ people paid" and enter how much each paid [staff reply, feedback forum](https://splitwise.uservoice.com/forums/162446-general/suggestions/3083636-allow-multiple-payers-in-expenses-that-span-multip).
2. **Itemization:** "Itemized: Enter individual items from a bill and assign them to specific people. You can also add tax, tip, and discounts. On the mobile app, Pro subscribers can itemize by scanning a receipt." [KB: ways to split](https://kb.splitwise.com/balances-and-expenses/what-are-different-ways-i-can-split-an-expense). Receipt scanning and itemization are listed as a Pro feature: "Only Pro subscribers can scan and itemize receipts, but all group members will see expenses created this way" [KB: What is Pro](https://kb.splitwise.com/pro/what-is-splitwise-pro), [splitwise.com/pro](https://www.splitwise.com/pro). Note that the KB is inconsistent about whether *manual* itemization without scanning is free: **UNVERIFIED**. Tax and tip are two fields that "automatically split… with the correct weight of all the people involved in the receipt" [user comment on feedback forum](https://splitwise.uservoice.com/forums/162446-general/suggestions/44842168-add-additional-custom-tax-tips-fees-to-itemized-re) (user signal; that weighting is proportional is **UNVERIFIED** from vendor docs). Splitwise also ships a separate free dinner-bill app, Plates, to "figure out tax and tip" [plates.splitwise.com](https://plates.splitwise.com/) (search snippet; page not read in full).
3. **Split doesn't add up:** When splitting unequally, "the remaining amount owed will show at the bottom of the screen/window" [staff reply, 2017](https://splitwise.uservoice.com/forums/162446-general/suggestions/3626523-unequal-bill-dividing-calculation). Saving a mismatched split is blocked with "The total of everyone's owed shares ($XX.XX) is different than the total cost ($YY.YY)" [user-quoted error, feedback forum](https://splitwise.uservoice.com/forums/162446-general/suggestions/3465674-when-editing-an-unequal-split-load-the-entered) (user signal; current wording **UNVERIFIED**). Partial or unassigned splits are not supported as far as found.
4. **Multi-currency:** By default each expense gets a currency label with no conversion. Balances are kept per currency ("You owe $12.45 and you are owed £8.72"), and changing the currency "only changes the currency label… it does not convert the amount" [KB: multiple currencies](https://kb.splitwise.com/balances-and-expenses/how-can-i-manage-a-friendship-or-group-with-multiple-currencies). Pro conversion converts **all** expenses in a group "at the current market exchange rate", including settled ones. New expenses need another tap of Convert, at the then-current rate [same KB](https://kb.splitwise.com/balances-and-expenses/how-can-i-manage-a-friendship-or-group-with-multiple-currencies). The rate is "the exchange rate at that moment" of conversion, from Open Exchange Rates, mid-market [KB: exchange rates](https://kb.splitwise.com/pro/how-are-exchange-rates-calculated-for-currency-conversion). **The rate is taken at conversion time, not locked at entry.**
5. **Who can edit / history:** Anyone involved in the expense or in its group can view, edit, or delete it. There are "no special permissions based on who originally added the expense", by design. Changes appear in Recent Activity / Activity, with optional notifications [KB: permissions](https://kb.splitwise.com/groups/can-i-prevent-group-members-from-changing-expenses-or-set-permissions). The store listing says "View your edit history for changes to an expense" and "Any deleted group or bill can be restored" [App Store](https://apps.apple.com/us/app/splitwise/id458023433). Anyone originally included can undelete [KB: restore](https://kb.splitwise.com/balances-and-expenses/how-can-i-restore-a-deleted-expense).
6. **Settlement view:** Simplify Debts is an optional group toggle that any member can flip. It minimizes the number of payments without changing totals, and it works per currency only [KB: Simplify Debts](https://kb.splitwise.com/balances-and-expenses/what-is-simplify-debts).
7. **Default entry flow:** Tap "Add expense" → enter description and amount. The sentence "Paid by [you] and split [equally]" is the default and needs no input [KB: ways to split](https://kb.splitwise.com/balances-and-expenses/what-are-different-ways-i-can-split-an-expense). That is roughly 2 fields + save. The exact tap count is **UNVERIFIED**. Free users are limited to 4 expenses per day [KB: What is Pro](https://kb.splitwise.com/pro/what-is-splitwise-pro). Pro adds saved default splits per group [KB: What is Pro](https://kb.splitwise.com/pro/what-is-splitwise-pro).

### 2.2 Tricount (bunq)

1. **Split modes:** Equally by default. Tap "Equally" to edit each participant's "share or amount" [help: manage expenses](https://help.tricount.com/articles/how-can-i-manage-my-tricounts-and-expenses). The vendor's own comparisons describe these modes as "Split evenly, by shares, or with custom amounts" [tricount vs Splid](https://tricount.com/comparisons/tricount-vs-splid). Play listing: "equally, by amount, or custom shares" [Google Play](https://play.google.com/store/apps/details?id=com.tribab.tricount.android). Percentage, adjustment, and multiple payers: **UNVERIFIED** (not found).
2. **Itemization:** No item-level split was found. The vendor contrasts itself with the receipt app Tab: "Attaching a receipt photo is not the same as automatically assigning its items". For tip, it says "Include the tip in the total you record and split that total as agreed" [tricount vs Tab](https://tricount.com/comparisons/tricount-vs-tab). Expense photos are free [App Store](https://apps.apple.com/us/app/tricount-split-settle-bills/id349866256). No receipt OCR was found (**UNVERIFIED** absence).
3. **Split doesn't add up:** Vendor guidance is "Check that all shares add up to the amount actually paid" [tricount vs Tab](https://tricount.com/comparisons/tricount-vs-tab), and the feature page says "Review the amounts assigned to each person, then save" [custom splits](https://tricount.com/features/custom-split-expenses). Whether the app blocks a mismatch: **UNVERIFIED**. Rounding is to 1 cent ("€100 by 3 → €33.34 / €33.33") [FAQ](https://help.tricount.com/articles/tricount-faqs).
4. **Multi-currency:** There is one tricount currency, and expenses can be entered in other currencies. "The amount is converted according to the market rate and the app provides you with a daily exchange rate" [help: manage expenses](https://help.tricount.com/articles/how-can-i-manage-my-tricounts-and-expenses). Conversion is free [tricount vs Splitwise](https://tricount.com/comparisons/tricount-vs-splitwise). Whether the rate is stored per expense or recomputed, and whether it can be edited by hand: **UNVERIFIED**.
5. **Who can edit / history:** "All participants have the ability to add their own expenses" [FAQ](https://help.tricount.com/articles/tricount-faqs). Edit steps cover date, amount, participants, currency, title, category, and type [help: manage expenses](https://help.tricount.com/articles/how-can-i-manage-my-tricounts-and-expenses). Edit permissions and edit history: **UNVERIFIED**.
6. **Settlement view:** The app computes over/underpaid amounts, then proposes repayments with the goal "to limit the number of transactions", so you may repay someone "who has never paid anything for me" [FAQ](https://help.tricount.com/articles/tricount-faqs). In other words, debts are simplified.
7. **Default entry flow:** Tap + → adjust the expense [help: manage expenses](https://help.tricount.com/articles/how-can-i-manage-my-tricounts-and-expenses). The participant you identify as in the tricount "will then be proposed to you as the payer each time you add an expense" [FAQ](https://help.tricount.com/articles/tricount-faqs). The split defaults to Equally. Field count: amount + title (inferred from the same pages). Exact taps: **UNVERIFIED**. Saved custom splits were a Premium feature that was removed and is "planned for a future update" [help: Premium](https://help.tricount.com/articles/what-happened-with-tricount-premium).

### 2.3 Settle Up

1. **Split modes:** Equal or "unequal weights", plus "multiple people paying for one item" [App Store](https://apps.apple.com/us/app/settle-up-group-expenses/id737534985). Members can have a default weight (for example "2" for a couple) [tips](https://settleup.io/tips). In the data model, `forWhom` takes decimal weights (e.g. `"2.3"`) and `whoPaid` is an array, so multiple payers are supported [API data entities](https://api.settleup.io/entities/). Exact-amount or percentage modes: **UNVERIFIED**. One App Store reviewer asks for the "Ability to assign a fixed amount to a person" and for adjustments [App Store review](https://apps.apple.com/us/app/settle-up-group-expenses/id737534985) (user signal).
2. **Itemization:** "Adding items from a long bill? Piece of cake!" [Google Play](https://play.google.com/store/apps/details?id=cz.destil.settleup). In the API, a transaction has `items[]`, each with its own amount and weighted `forWhom`: "first item main expense, second tip, third tax, you need to sum everything to get total" [API data entities](https://api.settleup.io/entities/). So tip and tax are separate items, each with their own sharers. Receipt *photos* are Premium [premium](https://settleup.app/premium). Receipt OCR: none found (**UNVERIFIED** absence).
3. **Split doesn't add up:** Weights are normalized, and the items sum *is* the total [API data entities](https://api.settleup.io/entities/). That means a weight split cannot fail to add up (inference from the model). Exact-amount mismatch handling: **UNVERIFIED**.
4. **Multi-currency:** "the exchange rate is automatically downloaded from a Yahoo service based on the current exchange rate for each day". It is shown on the transaction and is **editable**. After a manual edit, "all future transactions will use this exchange rate until you change back", and rates can also be changed for the whole group [tips](https://settleup.io/tips). Each transaction stores its own `exchangeRates` map and a `fixedExchangeRate` flag [API data entities](https://api.settleup.io/entities/). "Edit exchange rates in bulk" is Premium [premium](https://settleup.app/premium). **The rate is stored per expense at entry (daily granularity) and can be overridden.**
5. **Who can edit / history:** Per-user permissions are owner (30), read/write (20), or read-only (10), with a group default [API data entities](https://api.settleup.io/entities/). The store listing offers "give people read-only access" and "notifications about changes and history" [Google Play](https://play.google.com/store/apps/details?id=cz.destil.settleup). The server writes a `changes` record (action, by, entity) for every change [API data entities](https://api.settleup.io/entities/). Field-level diffs: **UNVERIFIED**.
6. **Settlement view:** Debt minimization is on by default ("you might end up paying to somebody you don't directly owe") and can be turned off per group [tips](https://settleup.io/tips). The server also generates `debts` with `minimizeDebts` as a group flag [API data entities](https://api.settleup.io/entities/).
7. **Default entry flow:** Tap a member's group circle to start an expense "with this member as the payer" [tips](https://settleup.io/tips). The "This is me" member is preselected as payer, and members' default weights are applied [tips](https://settleup.io/tips). A reviewer calls it "the fastest expense adding framework, because you can start by tapping the name of the person who paid" [App Store review](https://apps.apple.com/us/app/settle-up-group-expenses/id737534985) (user signal). Exact taps: **UNVERIFIED**.

### 2.5 Spliit (open source)

1. **Split modes:** `EVENLY` (default), `BY_SHARES`, `BY_PERCENTAGE`, `BY_AMOUNT` (source: `prisma/schema.prisma` `enum SplitMode`). Also marketed as "Split expenses by percentage, shares or amount" [spliit.app](https://spliit.app/). There is **one payer** per expense (`paidById`, source: `prisma/schema.prisma`). There is no adjustment mode and no itemized mode (source: `enum SplitMode`).
2. **Itemization:** None. "AI Scan" exists [spliit.app](https://spliit.app/), [README](https://github.com/spliit-app/spliit). The OpenAI prompt extracts only `amount`, `categoryId`, `date`, and `title` from the receipt, not line items (source: `src/app/groups/[groupId]/expenses/create-from-receipt-button-actions.ts`). Tax/tip handling: none found.
3. **Split doesn't add up:** **Save is blocked.** For `BY_AMOUNT`, the sum must equal the total, or validation fails with "The amounts add up to {sum}, {difference} more/less than the expense amount". For `BY_PERCENTAGE` the sum must be 100% (source: `src/lib/schemas.ts` `superRefine`; `messages/en-US.json` `amountSum`, `percentageSum`). Even and shares modes always add up by construction.
4. **Multi-currency:** The rate comes from Frankfurter for the **expense date** (`api.frankfurter.dev/v1/{date}?base=…`, daily granularity) (source: `src/lib/hooks.ts` `useCurrencyRate`). It is stored per expense as `conversionRate` along with `originalAmount`/`originalCurrency` (source: `prisma/schema.prisma`). The user can type a custom rate instead (source: `expense-form.tsx` `usingCustomConversionRate`). **The rate is locked per expense, keyed to the expense date, and can be overridden.**
5. **Who can edit / history:** There are no accounts ("No account" [spliit.app](https://spliit.app/)) and no permission model in the schema (source: `prisma/schema.prisma`). Anyone with the group link can edit. An activity log records create/update/delete expense with the acting participant and title, but not field-level diffs (source: `src/lib/api.ts` `logActivity`; `activity-item.tsx`).
6. **Settlement view:** Suggested reimbursements come from a greedy largest-creditor/largest-debtor match that minimizes transfers (source: `src/lib/balances.ts` `getSuggestedReimbursements`). "Optimize money transfers between participants" [spliit.app](https://spliit.app/).
7. **Default entry flow:** New expenses default to `EVENLY` with **all group participants** ticked at 1 share. The payer is the active user from localStorage (source: `expense-form.tsx` `getDefaultSplittingOptions`, `getSelectedPayer`). A per-group default split can be saved in localStorage (source: `saveDefaultSplittingOptions`). Common case: title + amount + save.

## 4. Implications for WatsTheSplit

### 4.1 Facts (from sections 2–3)

- **Partial / unassigned splits.** No surveyed app was found to save an expense that is only partly assigned and then let others fill in their own shares. Splitwise blocks a mismatched total and shows a "remaining" counter. Spliit blocks mismatched amount/percentage splits. Settle Up's weight and item model sums by construction. Tricount tells users to check that shares add up. Venmo, Splid, and Tricount enforcement is UNVERIFIED. Based on what could be verified, our collaborative "unassigned allowed" model is **rare, possibly unique** among these six apps.
- **Equal-split default.** Splitwise, Tricount, Spliit and Venmo Groups all default a new expense to an equal split across the whole group with the creator as payer. The common case is about 2 fields + save. Settle Up does the same using each member's default weight. In our app a new expense has no participants. Participants with no typed amount count as 0, and the common case takes about N + 4 actions over two screens.
- **Hybrid typed amounts + items.** Every surveyed app makes the user choose **one** split mode per expense. Splitwise's itemized mode is its own mode, with tax and tip fields. Settle Up has items, and each item has weighted sharers (main / tip / tax). Splitwise's "adjustment" mode (fixed delta per person, rest split equally) is the closest thing to mixing modes. No app was found that adds per-person typed amounts *on top of* item portions in one expense. Itemization is paid on Splitwise (scan, at minimum) and absent in Tricount, Splid, Spliit and Venmo.
- **FX locked per expense at creation.** Splitwise does not convert per expense: Pro converts the whole group at click time, using the same provider we use (Open Exchange Rates). Settle Up and Spliit **do** store a rate per expense at entry, but at **daily** granularity (Yahoo; Frankfurter for the expense date), and both let users override it. Tricount uses a "daily exchange rate". Its per-expense storage is UNVERIFIED. Locking a rate per expense is therefore **not unique**. What is uncommon in what we verified is the combination of an **hourly** rate, a **provider timestamp shown on the expense**, and **no rate drift on later edits**. We also offer no manual override, which Settle Up and Spliit both have.
- **Settlement.** Every surveyed app with a documented settlement view simplifies or minimizes transfers (Splitwise and Settle Up as a toggle). We show pairwise net only.
- **History.** Splitwise documents per-expense edit history and undelete. Settle Up and Spliit keep change or activity logs. We keep only the last editor.
- **Multiple payers.** These are supported by Splitwise, Settle Up and Splid. We support one payer.

### 4.2 Recommendations (opinion, derived from the facts above)

**Gaps to close (ordered by impact on the common case):**
1. **Default to equal split among all trip members, payer = me.** Pre-tick every member on create and treat untouched participants as an equal share of the remainder, not 0. Collapse the common case to name + total + save (matching Splitwise, Tricount, Spliit and Venmo). Keep the typed-amount and item tools as an "adjust" path. This also removes the main risk of our model: an expense nobody revisits currently leaves money owed to no one, because balances skip unassigned amounts.
2. **Make unassigned money impossible to forget.** If partial saves stay, surface unfinished expenses in the trip view and before settling. The trip list already shows a badge (`client/Trip.tsx`). Without this, the collaborative model quietly under-counts what the payer is owed.
3. **Offer simplified settlement as an option.** It is the norm everywhere surveyed. Pairwise net can stay as the "math" view.
4. **Edit history per expense.** "Anyone can edit" matches Splitwise, Spliit and Tricount. But those apps pair it with an activity log, notifications, or undelete, and we keep only the last editor.
5. **Manual rate override (optional).** Settle Up and Spliit both allow it for cases like "we used the booth rate". Weigh this against the "rate is locked" story. If added, record who overrode the rate and keep the provider rate visible.
6. Lower priority: multiple payers (Splitwise, Settle Up, Splid), and percentage/shares modes (Splitwise, Spliit, Settle Up).

**Differentiators worth keeping and saying out loud:**
- **Free itemization combined with per-person amounts in one expense.** No surveyed app mixes these. Splitwise puts scanning behind Pro, and Tricount, Splid, Spliit and Venmo have no items at all. The "spread proportionally" button covers the tax/tip case that Splitwise and Settle Up handle with dedicated fields.
- **Rate captured at the moment of entry with a visible provider timestamp.** This is a more precise version of what Settle Up and Spliit do (daily), and the opposite of Splitwise's convert-everything-later approach. Position it as "the rate when you paid, hourly, never re-converted", not as "the only app that locks rates", because that claim would be false.
- **Collaborative fill-in (each person claims their own share).** It is uncommon, so it is a real differentiator for restaurant-style bills, but only as an opt-in mode layered on an equal-split default, not as the default.
